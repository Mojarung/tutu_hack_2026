# Tutu MCP: что измерено живыми вызовами

Всё в этом файле получено **прямыми запросами** к `https://mcp.tutu.ru/mcp` 2026-08-19, а не
вычитано из документации. Каждая строка воспроизводится командой из раздела «Как повторить».

| Параметр | Значение |
|---|---|
| Сервер | `tutu-mcp-server` **0.40.0** |
| Транспорт | Streamable HTTP, **stateless** — сессия не выдаётся, `Mcp-Session-Id` в ответе отсутствует |
| Авторизация | нет |
| Версия протокола в ответе `initialize` | `2025-11-25` |
| Поддерживаемые версии | `2024-11-05`, `2025-03-26`, `2025-06-18`, `2025-11-25` |
| Полезная нагрузка | `result.content[0].text` — JSON строкой |

## Три ловушки транспорта, на которых теряется полдня

1. **Заголовок `MCP-Protocol-Version` обязателен для `tools/call`.** Без него сервер отвечает
   `HTTP 500` и телом `{"code":-32603,"message":"Error handling POST request"}` — то есть
   ошибка выглядит как проблема на стороне Tutu, хотя это отсутствующий заголовок.
   Работающее значение: `2025-06-18`.
2. **Тело запроса обязано уходить в UTF-8 байтами.** Кириллица в `origin` / `destination`,
   отправленная в системной кодировке Windows, даёт тот же `HTTP 500`. В клиенте тело
   сериализуется через `json.dumps(..., ensure_ascii=False).encode("utf-8")` и уходит как
   `content=`, не как `json=`.
3. **`initialize` вызывать не нужно** — сервер stateless. Лишний вызов только добавляет задержку.

## Пагинация: единственный способ узнать последнюю электричку

`meta.total_matched` отдаёт точное число офферов, `meta.total_matched_exact: true`.
Это и есть ключ ко всему продукту: **последнее отправление живёт на последней странице**,
и его номер вычисляется, а не подбирается перебором.

```
последняя_страница = ceil(min(total_matched, 300) / 30)
```

Потолок в 300 офферов жёсткий: `page ≤ 10`, `page_size ≤ 30`. Если `total_matched > 300`,
настоящее последнее отправление недостижимо — этот случай помечается как обрезанное окно
и подписывается в интерфейсе.

## Замеры по парам (дата запроса 2026-08-20, сортировка `departure_asc`)

| Пара | `total_matched` | Страниц | Первое отправление | Последнее отправление | Прибытие |
|---|---:|---:|---|---|---|
| Москва → Мытищи | 265 | 9 | 20.08 04:10 | **21.08 01:22** | 21.08 01:51 |
| Мытищи → Москва | 262 | 9 | 20.08 04:45 | **21.08 00:46** | 21.08 01:16 |
| Москва → Сергиев Посад | 56 | 2 | 20.08 04:40 | 21.08 00:58 | 21.08 02:31 |
| Сергиев Посад → Москва | 56 | 2 | 20.08 03:59 | 20.08 22:52 | **21.08 00:23** |
| Москва → Тверь | 23 | 1 | 20.08 04:27 | 20.08 21:37 | 21.08 00:56 |
| Тверь → Москва | 23 | 1 | 20.08 04:00 | 20.08 22:15 | **21.08 01:15** |

**Красная команда была права.** Мытищи 21.08 01:22 — это отправление следующих суток внутри
ответа на запрос за 20-е. Сравнение по времени суток («01:22 < 22:00, значит успеваю») напечатало
бы уверенно неверную последнюю электричку. Сергиев Посад и Тверь добавляют второй случай:
отправление сегодняшнее, а **прибытие домой уже завтра**. Дедлайн «дома к 22:00» обязан
сравниваться с прибытием как с моментом времени, не как со временем суток.

## Формат времени

`departure_at` и `arrival_at` приходят tz-aware: `2026-08-20T04:40:00+03:00`. Смещение отдаёт
сервер, продукт его не выдумывает и не подставляет. Внутри домена время переводится в минуты от
местной полуночи даты запроса, поэтому 01:22 следующих суток — это `1522`, а не `82`.

## Что отдаёт оффер

```jsonc
{
  "offer_id": "357e3da2f833853b269627fbd007d68a",
  "price": { "amount": 334.0, "currency": "RUB" },
  "duration_min": 95,
  "departure_at": "2026-08-20T04:40:00+03:00",
  "arrival_at":   "2026-08-20T06:15:00+03:00",
  "checkout_url": "https://www.tutu.ru/rasp.php?st1=45807&st2=48507&date=20.08.2026",
  "legs": [{ "segments": [{
      "from": "Москва — Ярославский вокзал (2000002)",
      "to":   "Сергиев Посад, 2000753",
      "voyage_no": "6302",
      "vehicle_meta": { "name": "Электричка", "code": "simple" }
  }]}]
}
```

Отсюда берётся **настоящее имя вокзала отправления** — продукт не угадывает, с какого вокзала
идёт электричка, а показывает то, что вернул Tutu.

## `search_hotels` — материал для лестницы спасения

Параметр называется `city_name` (не `city`; `city` даёт ошибку). Ответ содержит координаты,
поэтому расстояние от станции до отеля считается, а не выдумывается:

```jsonc
{
  "name": "Лафер Ренессанс", "stars": 4, "rating": 7.06, "review_count": 49,
  "location": { "lat": 56.315228, "lng": 38.23016 },
  "best_offer": { "room_name": "Стандарт",
                  "price": { "amount": 3400.0, "currency": "RUB" },
                  "price_basis": "stay_total", "free_cancellation": true },
  "checkout_url": "https://hotel.tutu.ru/offers/details?..."
}
```

`price_basis: "stay_total"` — цена уже за весь период. Умножать на ночи нельзя.

## Тайминги одного клиента

| Вызов | Время |
|---|---:|
| `tools/call search_etrain`, одна страница | 0.4–0.9 с |
| `tools/call search_hotels` | 1.5–2.5 с |
| `fetch_resource tutu://status` | 0.3 с |

Рейт-лимита при последовательных и параллельных вызовах в 8 потоков не наблюдалось.
Утверждать, что его нет под нагрузкой демо-дня, нельзя — клиент держит потолок
одновременных запросов и экспоненциальный бэкофф, см.
[`../adr/0004-caching-and-degradation.md`](../adr/0004-caching-and-degradation.md).

## Как повторить

```bash
uv run --directory backend python -m obratno.cli probe --origin Москва --destination Мытищи --date 2026-08-20
```

Команда печатает ровно ту таблицу, что выше: число офферов, число страниц, первое и последнее
отправление с датой.
