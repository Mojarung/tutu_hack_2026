# ADR 0001 — Свой тонкий клиент Tutu MCP вместо SDK

**Статус:** принято, 2026-08-19

## Контекст

Продукту нужен ровно один транспорт: `tools/call` к `https://mcp.tutu.ru/mcp` по Streamable HTTP,
с ретраями и потолком параллельных запросов. Живые замеры
([`../mcp/probe-log.md`](../mcp/probe-log.md)) показали, что сервер **stateless**: `initialize`
не выдаёт `Mcp-Session-Id`, а `tools/call` работает самостоятельным POST-запросом.

## Варианты

1. **Официальный `mcp` SDK.** Полная реализация протокола, включая то, чего здесь нет: сессии,
   уведомления, sampling, elicitation. Тянет свой стек HTTP и свой жизненный цикл соединения.
2. **`fastmcp`.** То же плюс серверная часть, которая не нужна: своего MCP-сервера мы не публикуем.
3. **Свой клиент на `httpx`** — около 120 строк: сборка JSON-RPC, заголовки, разбор
   `result.content[0].text`, ретраи `tenacity`, семафор.

## Решение

Вариант 3.

Причины конкретные, а не стилистические:

- **Два бага транспорта, которые нужно держать в своих руках.** Без заголовка
  `MCP-Protocol-Version` сервер отвечает `HTTP 500`; тело обязано уходить UTF-8 байтами, иначе
  снова `500`. И то и другое — про то, как именно формируется запрос. В своём клиенте это две
  строки и два теста, через SDK — борьба со слоем, который эти детали прячет.
- **Единственный сценарий нагрузки — веер.** До 300 вызовов на одну дату. Управление потолком
  параллелизма, бэкоффом и кэшем — центральная часть продукта, а не деталь клиента.
- **Ноль лишних зависимостей** в слое, который целиком покрывается тестами на `respx`.

## Последствия

- Клиент живёт в `backend/src/obratno/infrastructure/mcp_client.py`, не знает домена и
  переиспользует один пул соединений `httpx.AsyncClient`.
- Если Tutu перейдёт на stateful-сессии, добавится один шаг рукопожатия. Это отражено в тестах:
  контракт транспорта проверяется отдельно от контракта данных.
- Прикладной код не зависит от версии протокола: она задаётся одной константой `MCP_PROTOCOL`.
